# 提交結果與重試恢復

磁力提交及原生 RETRY 的持久化標記，在認證完成、即將送出相應 POST 時才設置。準備資料夾、登入或本機冷卻檢查失敗，不代表下載已經提交。

收到明確拒絕時，先清除該次提交標記，再處理冷卻儲存或重新登入。即使冷卻狀態不能寫入，或重新登入期間程序停止，也不會將已拒絕的請求誤判為結果未知。冷卻與帳號健康檢查仍會限制何時能再次操作。

| 失敗位置 | 持久化狀態與恢復方式 |
| --- | --- |
| 尚未送出磁力／RETRY（例如認證或資料夾準備失敗） | 可手動重試；不自動重送已失敗任務 |
| 明確拒絕（例如 401／429） | 清除提交標記，允許在雲端可用後重試 |
| POST 逾時、5xx、成功回應損壞，或送出途中程序停止 | 保留待確認及來源占用；重啟不能繞過 |
| 已保存 cloud task/file ID，只有輪詢或 aria2 RPC 失敗 | 沿用原 ID／GID 接續，保留來源與下載檔案 |

`before_send` 與 `on_rejected` 回呼必須同步完成 SQLite 寫入；寫入失敗時不繼續發送。認證拒絕後的一次重新發送會重新設置標記，因此第二次回應遺失仍然受保護。

這不是將所有「待確認」自動轉為可重試。對真正未知的 POST，雲端列表暫時查不到並不足以證明未建立；必須保留來源保護，核對原任務／file_id，或經獨立完整查證後進行有備份的人工修復。此次更新不修改既有任務或批次解除標記。

回歸測試使用模擬 HTTP、隔離 SQLite 及程序中斷，不連接正式 PikPak，不提交下載。另以測試專用 localhost aria2 驗證下載／重啟續傳。
